Volume at price: which levels a stock will actually defend

This is a revision note, not a session brief. It records what I learned building a volume-profile tool in quant-lab — the thing I now reach for when I want to know which price levels a stock is likely to actually defend.

The short version: a price level matters in proportion to how much stock changed hands there, and a bar's closing price tells you almost nothing about that. Most of the work is refusing three tempting shortcuts in a row.

Getting the data at all

First problem, and it is a boring one: I have Bloomberg, but only inside Citrix. BLPAPI needs the Terminal running on the same machine — a published Citrix session does not expose the local API socket to my Mac. So the only Bloomberg path is =BDH() in Excel inside Citrix, save a CSV, copy it across. Fine once; useless as a pipeline. I stopped trying to build around it.

That leaves yfinance. Its interval limits are quoted inconsistently online, so I measured them rather than trusting docs:

IntervalActual depthBars retrieved
1d1980-12-12 → today11,515
1hlast 730 days5,073
15m / 5mlast 60 days1,560 / 4,680
1mlast 7 days2,730

That table decides the whole design. 5m would be the natural resolution for level work, but 60 days is far too short a window to establish where inventory sits. 1h over 730 days is the only setting that is simultaneously fine-grained enough and long enough. So 1h it is.

One consequence worth writing down, because it is not obvious: Yahoo serves a rolling window. The 5-minute bars from 90 days ago are gone and no request will bring them back. So my downloader merges into a Parquet file instead of overwriting it — which means running it on a schedule slowly accumulates intraday history that I could never fetch in one go.

Shortcut #1: counting time at price

The first instinct is to ask where price spent time: chop the range into 100 bins and count how many hourly bars closed in each.

counts, edges = np.histogram(window["close"], bins=100)

This is wrong in a specific way. Every hour counts the same, so a dead pre-holiday session weighs exactly as much as a panic session with fifty times the volume. Time spent is not conviction. What creates a level that gets defended later is positions, and positions come from volume.

Shortcut #2: putting the volume at the close

Obvious fix — same histogram, weighted by volume:

vol_by_close, _ = np.histogram(window["close"], bins=100, weights=window["volume"])

Better, and the shape genuinely changes. But it still assumes every share traded in that hour changed hands at the closing price. Here is the widest MSFT bar in my 12-month window:

bar at 2026-04-08 13:30
  low       432.44
  high      451.73   <- travelled 19.29 (4.5%)
  close     447.20
  volume 45,559,586 shares, spread across that whole range

45.5 million shares got dumped into the single bin containing 447.20, when they demonstrably traded across a $19 range. On a volatile day — exactly the days that build the levels you care about — this is at its most wrong.

The fix: spread each bar across its range

Without tick data the honest assumption is that volume was distributed evenly across the range the bar travelled. Each bin then receives volume in proportion to how much of the bar's range it covers:

overlap = min(bar_high, bin_top) - max(bar_low, bin_bottom)
share   = overlap / (bar_high - bar_low)

Two checks make this safe, and I would not trust the output without both. The shares for a single bar must sum to exactly 1 — otherwise you are inventing or destroying volume — and the finished profile must total the raw data:

shares sum to 1.000000  (must be 1.0 - no volume invented or lost)

total volume in profile: 5,402,122,519
actual total volume:     5,402,122,519   <- must match

I wrote the slow, readable loop version first, then checked the vectorised implementation against it: largest difference: 0.000000. That comparison is the only reason I trust the fast one.

POC and the value area

Two numbers come out of the finished profile:

  • POC (Point of Control) — the single price with the most volume. The market's centre of gravity: the price the most participants have a cost basis at, which is what gives it its pull.
  • Value area — the band around the POC holding 70% of all volume. The "normal" range; outside it, price is stretched.

MSFT over the last 12 months of hourly bars:

spot            483.35
POC             399.31   -17.4%
value area      364.54 -> 479.07   (-24.6% / -0.9%)

position: ABOVE value area - stretched

Price is 17% above the level where the most volume actually traded, with a low-volume node at 468.84 holding only 12% of surrounding volume — thin air, nothing to catch a retreat.

This is a statement about positioning, not a forecast. "Price returns to the POC" is a tendency, not a schedule, and a stock in a strong trend can sit above its POC for a year.

Volume goes stale, and it matters more than I expected

A trade from eleven months ago describes inventory that has almost certainly turned over. So I added an exponential decay — at a 90-day half-life, volume from 90 days ago counts half as much as today's. I expected this to nudge the numbers. On MSFT it inverted the conclusion:

      no decay   POC    399.31 ( -17.4%)   value area 364.54 -> 479.07
180d half-life   POC    370.67 ( -23.3%)   value area 364.54 -> 456.57
 90d half-life   POC    370.67 ( -23.3%)   value area 364.54 -> 448.39
 30d half-life   POC    483.16 (  -0.0%)   value area 391.13 -> 513.84

At a 30-day half-life the POC is 483.16 — sitting exactly on spot. Recent trading has built a fresh shelf up here that the year-long profile buries under old volume. Same data, opposite answer to "is MSFT stretched?".

There is no correct half-life. But the lesson generalises: any indicator with a lookback window has a setting that flips its conclusion, and if I have not looked at that sensitivity I do not actually know what the indicator is telling me. Quoting a POC without stating the window is close to meaningless.

Comparing across stocks

Since names trade at different prices, the comparable figure is the distance from spot to POC in percent (90-day half-life, 12-month window):

TickerSpotPOCDistanceZone
MSFT483.35370.67−23.3%above value area
NVDA214.75208.64−2.9%inside
AAPL309.42310.32+0.3%inside

A large negative distance means price has run far above where volume actually traded, with no shelf of real inventory beneath it. inside means price is at fair value with volume support right where it stands.

Where the code lives

A process lesson that turned out to matter as much as the method. I split the work:

  • .py for anything with a right answer — the profile maths, the cache logic. Notebooks run cells out of order, so a function can quietly depend on state that no longer exists. For code whose bugs are silent and numerical, that is disqualifying.
  • .ipynb for judgement — which window, what half-life, does this look sane. Iterative and visual, which is what notebooks are actually good at.

The glue is autoreload, so editing the module updates the notebook without restarting the kernel and re-downloading everything:

%load_ext autoreload
%autoreload 2

import sys, pathlib
sys.path.insert(0, str(pathlib.Path.cwd().parent))

import marketdata as md

That sys.path line took me a minute to understand, so: Python only imports from directories listed in sys.path. The notebook runs in notebooks/, but marketdata.py sits one level up in quant-lab/, so without this line import marketdata raises ModuleNotFoundError. insert(0, ...) rather than append puts it at the front of the search order, so my file wins over any installed package of the same name.

The str() is there because sys.path holds strings, while pathlib.Path.cwd() returns a Path object. Both name the same directory; the difference is that a Path knows it is a path and carries .parent, .exists(), and the / operator, where a plain string needs os.path.dirname and os.path.join wrapped inside-out around it. The rule I settled on: pathlib inside my own code, str() only at the boundary where an older API insists — and sys.path is one of the genuine holdouts, since it predates pathlib by about two decades.

The payoff of the split showed up immediately: I derived the profile by hand in the notebook, checked it against the module, and from then on just called the function. Verified once, reused everywhere, never re-pasted.

Status

Closed — I can state these without looking them up:

  • Bloomberg via Citrix cannot drive a local data pipeline; BLPAPI needs the Terminal on the same machine
  • yfinance intraday is a rolling window — 1h/730d, 5m/60d, 1m/7d — so a merging cache accumulates history that cannot be re-requested
  • A bar's volume must be spread across its [low, high] range, not assigned to its close; shares per bar must sum to 1
  • POC = heaviest price level; value area = the 70%-of-volume band around it
  • Any lookback-windowed indicator has a setting that flips its conclusion — check the sensitivity before quoting the number
  • Maths belongs in .py, judgement in .ipynb, joined by %autoreload 2
