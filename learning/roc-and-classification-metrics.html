ROC, AUC, and what a classification score actually tells you

This is a revision note, not a session brief. It pulls together everything on ROC and AUC that has come up in real work since June, marks honestly what is closed and what is still open, and ends with the one exercise that would close the rest.

The short version: AUC is a ranking metric. It answers one question — if I draw one winner and one loser at random, how often does the model score the winner higher? It answers nothing else. Most of the mistakes below come from asking it a question it does not answer.

What AUC measures

Take every score the model produced, split them by the true label, and lay the two distributions on top of each other. AUC is the probability that a randomly drawn positive sits to the right of a randomly drawn negative.

That is the whole definition. Two consequences fall straight out of it, and both matter later:

  • AUC is invariant to any monotone transform of the scores. Squaring every score, or passing them all through a sigmoid, changes no ordering, so AUC does not move. This is why AUC cannot detect a miscalibrated model.
  • AUC never involves a threshold. Accuracy, precision, recall and F1 all pick one operating point. AUC averages over all of them.

The ROC curve is the same information drawn differently: sweep the threshold from high to low, and plot the true-positive rate against the false-positive rate at every step. The area under that curve equals the probability above.

Definition, so it stops being jargon: true positive rate (also sensitivity, also recall) is the share of actual positives you caught. False positive rate is the share of actual negatives you wrongly flagged. A perfect model catches everything while flagging nothing — the top-left corner.

The mistake this is really about

Recorded in the Kaggle plan as finding 1, and not yet reproduced by hand — the Week 1 task that asks you to re-run it is still unticked:

y_pred = clf.predict(x_test)        # returns 0/1 LABELS
fpr, tpr, threshold = roc_curve(y_test, y_pred)
print(roc_auc_score(y_test, y_pred))

.predict() has already applied a threshold. Feeding two-valued input to roc_curve gives a curve with exactly one interior point, so the "AUC" you read off is not the AUC — it collapses to (sensitivity + specificity) / 2, which is the balanced accuracy.

I generated a clean demonstration rather than assert it. Same model, same test set, scored both ways:

quantity value
AUC on predict_proba(X)[:, 1] 0.7177
"AUC" on predict(X) 0.6787
balanced accuracy on predict(X) 0.6787
understated by 0.0390

The second and third rows are identical to four decimal places, which is the proof — the hard-label "AUC" is the balanced accuracy wearing a different name. The script asserts this equality on every run, so if it ever stops being true the figure build fails instead of quietly printing a wrong number.

Why this is not a small thing: 0.039 of AUC is a large amount of understated skill. On a leaderboard it is the difference between "this model is mediocre" and "this model is fine, my measurement was broken."

playground-series-s6e6/model.ipynb — the stellar-class problem — has the same split-brain, verified by reading it today:

  • cell 12 computes classifier.predict_proba(x_test) and displays it
  • cell 13 immediately overwrites y_pred with classifier.predict(x_test)

Here it did not cause a silent understatement, because the target has three classes and roc_curve refused outright with "multiclass format is not supported". You commented the ROC out and fell back on balanced_accuracy_score plus classification_report. That fallback was the right call — but notice what happened: an error message stopped the multiclass version, whereas in the binary case the identical mistake produces a plausible number and no complaint at all.

That is the pattern worth carrying: the dangerous version of a bug is the one that returns a number instead of raising. It is the same lesson as the string-vs-int comparison in Mission 8, where '18' == 18 was silently False.

Which metric answers which question

flowchart TD
    Q["What do I actually want to know?"] --> R["Can it rank?<br/>Are winners scored above losers?"]
    Q --> C["Are the probabilities honest?<br/>Does 0.7 mean 70%?"]
    Q --> D["Is it right at the threshold I trade at?"]

    R --> AUC["ROC AUC<br/>needs predict_proba<br/>threshold-free, monotone-invariant"]
    C --> LL["log loss / Brier<br/>reliability diagram<br/>fix: Platt or isotonic"]
    D --> PR["precision / recall / F1<br/>confusion matrix<br/>at one chosen cut"]

    AUC -.->|"blind to"| C
    LL -.->|"blind to"| R

The dotted arrows are the useful part. A model can have AUC 0.95 and probabilities that are systematically wrong; calibration fixes the probabilities and leaves AUC untouched, because calibration is a monotone transform. If you are scored on AUC, calibration cannot help you. If you size positions off the score, it is everything.

Live example of that second case: ma_cross.py computes confidence = abs(ma_fast - ma_slow) / price * 50, and sizer.py multiplies position size by it. That number has never been calibrated against anything. It is being used as if it were a probability.

My own AUCs, dated

date run OOF AUC source
2026-06-20 meta-label v1, 5 tickers, fixed 10-bar label 0.565 session brief
2026-08-09 same label, 15 tickers 0.562 session brief
2026-08-09 triple-barrier label (stop / target / time) 0.631 session brief

Read against the definition at the top: 0.565 means that given one winning trade and one losing trade, the model puts them in the right order 56.5% of the time. A coin does it 50% of the time. That is a real edge and a small one, and stating it in those words is a better guard against over-excitement than any amount of Sharpe.

The August result, and why it is the most useful thing here

On 2026-08-09 the label changed from "hold 10 bars no matter what" to triple-barrier — first touch of stop, target, or time limit. Two numbers moved in opposite directions:

  • AUC rose, 0.562 → 0.631
  • the reported Sharpe uplift collapsed, +3.86 → about +0.67

Both are correct, and they are not in conflict, because they answer different questions. The model genuinely got better at predicting the thing it was asked to predict. What fell was the inflated uplift that came from the old label describing a trade the engine would never have held. The model improved and the headline number got worse, at the same time, for the same reason.

The statistics half: AUC is an estimate, and it has an error bar

This is the part that is open. Every AUC above is a point estimate from one sample. None has a confidence interval, so none of the gaps between them is known to be real.

Two things to learn here, in order:

  1. AUC is the Mann–Whitney U statistic, rescaled. U / (n_pos · n_neg) is exactly the probability defined at the top. This matters because it means the whole non-parametric two-sample apparatus — including standard errors — already applies to AUC. It is not a bespoke ML quantity.
  2. The bootstrap gives the interval without any distributional assumption. Resample the out-of-fold predictions with replacement ~1000 times, recompute AUC each time, take the 2.5th and 97.5th percentiles. From the Kaggle plan: "Do this once on your S6E7 OOF and you will never again get excited about a +0.0004 gain."

The trap that is specific to my data

There is a catch that does not apply to a Kaggle tabular problem but does apply to every AUC in the table above. On 2026-08-09 the mean label uniqueness came out at 0.14 — the labels overlap heavily in time, so 59,500 samples carry roughly 8,300 observations' worth of independent information.

A bootstrap that resamples 59,500 rows as if they were independent will therefore produce an interval that is far too narrow — optimistic by roughly sqrt(1/0.14) ≈ 2.7× if the naive comparison holds. The right fix is to resample blocks of non-overlapping observations rather than individual rows. This is unresolved and is the same effective-sample-size problem already flagged against the PSR/DSR calculation.

Status

Closed — I can state these without looking them up:

  • AUC is P(random positive outranks random negative); 0.5 is no skill
  • AUC is threshold-free and invariant to monotone transforms
  • AUC and downstream P&L answer different questions (learned the hard way, 2026-08-09)
