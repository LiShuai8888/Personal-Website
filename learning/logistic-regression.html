Logistic regression: from a linear score to an honest probability

A revision note in the same spirit as the ROC one: what I actually understand about logistic regression after building it by hand on the screen-time addiction set (playground-series-s6e8), not what I have merely read. Every number below was generated from that data.

The one-line version: logistic regression is linear regression on the log-odds, squashed into a probability by the sigmoid. It keeps the ranking a plain linear fit would give you and adds the one thing that fit could not — an output bounded to [0, 1] that you can read as a probability.

Why not just use linear regression?

On a 0/1 target a linear fit produces a usable ranking — on this data it scored AUC 0.91 — but its output is unbounded. Fitting a straight line to addicted_label gave predictions from −0.163 to 1.693. A "probability" of 1.693 is meaningless, and there is nothing in the model to stop it. Logistic regression plugs exactly that hole.

The sigmoid: any real number, squashed into (0, 1)

The fix is one function. Take the linear score and pass it through the sigmoid (the logistic function, which names the model):

sigma(z) = 1 / (1 + e^(−z))

It is an S-curve: z = 0 maps to 0.5, large positive z approaches 1, large negative z approaches 0, and it never quite reaches either end. So whatever the linear part produces — 47 or −300 — the sigmoid hands back a valid probability. That is the whole repair.

Two stages: a linear score, then a squash

For each person the model does exactly two things. First a linear stage, identical in form to linear regression:

z = w·x + b

then a squash, p = sigma(z). That raw z has a name — the log-odds (or logit), because z = ln( p / (1 − p) ). "Odds" is p/(1−p): a probability of 0.8 is odds of 4, i.e. 4-to-1. The linear part predicts the log-odds; the sigmoid inverts that back into a probability.

This is not a metaphor. decision_function returns z, predict_proba returns the sigmoid of it, and they match to floating point:

z = clf.decision_function(x_test)     # raw linear score  w·x + b   (the log-odds)
p = clf.predict_proba(x_test)[:, 1]   # probability of class 1
# p == 1 / (1 + np.exp(-z))           -> True, for every row

One payoff of the log-odds view, useful for anyone from a stats background: each coefficient wⱼ reads as "one more unit of feature j adds wⱼ to the log-odds," i.e. multiplies the odds by e^(wⱼ) — an odds ratio.

Same ranking, real probabilities

modeloutput rangeAUC
linear regression−0.163 to 1.693 (escapes [0, 1])0.9108

Two things at once. The output is now bounded — a genuine probability you can read as "82% likely" — where the linear fit escaped to 1.693. And the AUC is essentially unchanged, because the sigmoid is monotonic: higher z always gives higher p, so it never reorders anyone, and AUC only cares about order (the whole point of the ROC note). Logistic regression = the linear fit's ranking, plus probabilities you can actually use.

How it learns, and why it warned

Linear regression solves for its weights with one formula. Logistic regression cannot — there is no closed form. It searches for the weights by iterative optimisation: the lbfgs solver starts somewhere and steps downhill on the loss (log loss / cross-entropy) toward the minimum, and max_iter caps how many steps it may take. The default is 100.

That search is easy on a round loss surface and slow on a stretched one — and mine was stretched, because the features live on wildly different scales:

notifications_per_day swings by ~63, gaming_hours by ~0.85 — a 70× gap. That deforms the loss surface into a long, narrow ravine; the solver zig-zags down it slowly and runs out of its 100 steps before reaching the bottom, returning half-optimised weights. That is the ConvergenceWarning. Same model, same cap, unscaled vs scaled:

The warning is not cosmetic: the unscaled model was genuinely worse (AUC 0.8951 vs 0.9115) because it quit before finishing. Silencing it with max_iter=1000 works, but it is a band-aid — it just buys more steps down the same bad ravine.

The fix: scale, then wire it in a pipeline

The real fix reshapes the problem. StandardScaler turns each feature into a z-score — subtract its mean, divide by its std, so every feature has mean 0 and std 1. The ravine becomes a round bowl and the solver converges in 12 steps instead of 100+.

Same discipline as median imputation: learn the means and stds on training data only, then apply them to the test set — never over the whole table (leakage). The clean way to guarantee that is a pipeline, which also re-applies the transform automatically at predict time:

from sklearn.preprocessing import StandardScaler
from sklearn.pipeline import make_pipeline

clf = make_pipeline(StandardScaler(), LogisticRegression())
clf.fit(x_train, y_train)                     # scales, then fits
y_proba = clf.predict_proba(x_test)[:, 1]     # auto-scales x_test with TRAIN stats

One rule to carry: scaling matters for gradient- and distance-based models — logistic regression, SVM, KNN, neural nets. It does nothing for tree-based models (decision trees, random forests, gradient boosting), which split on thresholds and ignore magnitudes. That is exactly why only the logistic cell warned and the tree cells did not.

The trading translation is exact: throwing raw price levels (thousands) and returns (0.01) into the same gradient fit without normalising lets the big-scale variable hijack every step, and the optimiser crawls. Standardising to z-scores is the same move as using vol-normalised features in a factor model — put everything in comparable units so no single feature dominates by scale alone.

The output layout: predict_proba vs predict

predict_proba(x_test) returns one row per person and one column per class, in clf.classes_ order:

clf.classes_        -> [0 1]
predict_proba shape -> (138274, 2)   # [P(class 0), P(class 1)] per row
first rows:
 [[0.4603 0.5397]
  [0.1791 0.8209]
  [0.9802 0.0198]]
each row sums to 1

So column 0 is P(not addicted), column 1 is P(addicted), and the two always sum to 1 — column 0 is just 1 − column 1. For a probability of addiction you take predict_proba(x_test)[:, 1]. predict(x_test), by contrast, throws all of that away and returns a hard 0/1 at the 0.5 cut — the mistake that flattens a ROC curve to a single kink and understates AUC (see the ROC note). Score AUC on predict_proba[:, 1], never on predict.

Status

Closed — I can state these without looking them up:

  • logistic regression = linear score z = w·x + b, then p = sigma(z); predict_proba[:, 1] is literally sigmoid(decision_function)
  • z is the log-odds, ln(p/(1−p)); a coefficient is an odds ratio in log space
  • the sigmoid is monotonic, so logistic keeps the linear fit's ranking (same AUC) and adds bounded probabilities
  • no closed form → iterative solver → unscaled features stretch the loss surface → ConvergenceWarning, and the under-fit costs real AUC (0.8951 vs 0.9115)
  • StandardScaler is the fix (12 vs 100+ iters); trees never need it; wire it in a pipeline to avoid leakage
  • predict_proba is [P(0), P(1)]; take column 1; never score AUC on predict()
